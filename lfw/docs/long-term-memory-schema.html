HARNESS V2 · SCHEMA · 2026-10-16

장기기억 스키마

MemoryGraph는 확정된 지식, memory_candidates는 검토 전 후보와 저장 계획을 보관한다. 두 구조를 분리해 정의하고 연결 필드만 공유한다. 조회·저장 순서와 실패 처리는 운영·구현 문서를 참고한다.

두 저장소Memory기억 타입관계후보저장 계획연결·제약

1. 두 스키마의 경계

MemoryGraph DB

<git-common-dir>/harness-data/memorygraph.db · 기본 테이블 memories(기억), relationships(관계). 라이브러리가 구조를 관리한다.

Harness State DB

<git-common-dir>/harness-data/state.db · memory_candidates(후보). Harness 스키마와 상태 저장 함수가 구조를 관리한다.

아래 Memory·Relationship은 라이브러리의 논리 객체 계약이다. SQLite의 실제 컬럼 이름과 차이가 있는 곳은 별도로 표시한다. 전체 정본은 고정 버전 models.ts, SQLite backend, Harness schema.sql이다.

2. Memory · 기억 한 건

문제·해결책·명령은 서로 다른 테이블이 아니라 같은 Memory 구조의 type(분류) 값이다. 라이브러리의 공통 필드와 하네스가 저장 계획으로 지정하는 필드를 구별한다.

필드값·기본값설명
id객체 생성 전 선택 / 저장 시 식별자기억 ID. Harness create는 candidate:<candidate_id>를 사용한다.
type필수 / 공식 13개 값기억의 용도·종류. 임의 문자열을 추가하지 않는다.
title필수 / 1~200자검색할 수 있는 짧은 제목.
content필수 / 비어 있지 않은 본문대화 원문 없이도 이해되는 지식.
summary선택 / 최대 500자짧은 요약. Recall은 없으면 본문을 잘라 보완한다.
tags문자열 배열 / 기본 []소문자·공백 정규화된 분류 태그. SQLite에서는 JSON TEXT.
importance0~1 / 기본 0.5중요도. Recall 동점 정렬에도 사용.
confidence0~1 / 기본 0.8기억 내용의 근거 확신도.
context선택 / 객체프로젝트·파일·기술 등 적용 맥락. SQLite에서는 JSON TEXT.
effectiveness선택 / 0~1사용 효과. 현재 Harness 저장 계획이 직접 지정하지 않음.
usage_count0 이상 정수 / 기본 0사용 횟수. 기억 저장 가치 점수와 다르다.
created_at, updated_at시각 / 기본 현재 시각생성·갱신 시간.
last_accessed선택 / 시각마지막 접근 시간.
version, updated_by1 이상 정수·기본 1 / 선택 문자열라이브러리의 갱신 메타데이터. 후보 테이블의 버전이 아니다.
context와 조회 보강 필드

context는 project_path, files_involved, languages, frameworks, technologies, git_commit, git_branch, working_directory, timestamp, session_id, user_id, additional_metadata, tenant_id, team_id, visibility, created_by를 지원한다. 배열은 기본 [], 추가 메타데이터는 {}, visibility는 private/project/team/public 중 기본 project다. 이는 라이브러리 지원 범위이지 Harness의 로그인·팀 권한 구현을 뜻하지 않는다.

Harness writer는 additional_metadata.harness_candidate_id와 harness_plan_fingerprint로 후보·계획을 추적한다. 조회 객체의 relationships, match_info, context_summary는 보강 정보이며 memories 테이블의 독립 컬럼이 아니다.

3. Memory.type · 공식 기억 타입 13개

값의미값의미
task작업 지식code_pattern재사용 코드 패턴
problem문제·제약solution해결책·설계 선택
project프로젝트 배경technology기술·도구 지식

공식 decision 타입은 없다. 설계 결정은 예를 들어 solution + decision 태그로 표현한다. 우선 기존 타입과 태그를 사용하고, enum(허용값 목록) 확장은 필요성이 확인된 뒤 모델·검증·저장·조회 경로를 함께 수정한다.

4. Relationship · 기억 사이의 방향 관계

solution Memory ── SOLVES(해결함) ──→ problem Memory
객체 필드설명·제약
id관계 식별자. 객체 생성 전 선택값.
from_memory_id, to_memory_id출발·도착 기억 ID. 비어 있지 않아야 하며 SQLite 실제 컬럼은 from_id, to_id다. memories의 외래키이며 기억 삭제 시 관계도 삭제된다.
type공식 관계 35개 중 하나. SQLite 컬럼은 rel_type.
properties아래 관계 속성 객체. SQLite에서는 각 속성을 컬럼으로 저장한다.
description, bidirectional논리 모델의 선택 설명·기본 false인 양방향 표시. 고정 SQLite 테이블에는 대응 독립 컬럼이 없으며 Harness 계획 입력에도 없다.

관계 속성

strength(연결 강도·기본 0.5)와 confidence(관계 확신도·기본 0.8)는 0~1이다. context는 관계 이유다. evidence_count(기본 1), validation_count·counter_evidence_count(기본 0)는 근거·검증·반증 횟수이며 음수가 아닌 정수다. success_rate는 선택적인 0~1 성공률이다.

created_at, last_validated, valid_from, recorded_at은 생성·마지막 검증·효력 시작·기록 시각으로 기본 현재 시각이다. valid_until은 선택적인 효력 종료 시각, invalidated_by는 무효화 근거 참조다. Harness의 저장 계획은 방향·대상·타입·강도·확신도·관계 맥락만 받는다.

Entity·Outcome 등 보조 구조의 범위

라이브러리의 고급 모듈에는 본문 대상 추출 Entity와 기억 사용 결과 Outcome 같은 보조 개념이 있다. 현재 Harness의 SQLite 조회·저장 경로가 이들을 자동 생성·조회하는 것은 아니며, 위 35개 일반 관계 목록과도 구별한다. 임의 노드 라벨을 추가하는 기능으로 해석하지 않는다.

5. memory_candidates · 검토 전 후보

Harness State DB의 실제 컬럼 사전이다. PK는 고유 기본키, FK는 다른 행을 가리키는 외래키다. 후보는 발견 즉시 한 건씩 저장하며 관계는 최종 저장 계획에서 정한다.

컬럼형식·필수의미·제약
idTEXT PK · 필수불변 후보 ID. 현재 생성 함수 기본 접두사는 MEMC.
run_idTEXT FK → runs.id · 필수발견 당시 Run. 후보 생성은 running Run에서만 허용.
proposed_typeTEXT · 필수위 13개 기억 타입 중 초안. 최종 저장 타입과 달라도 됨.
titleTEXT · 필수공백 제거 기준 1~200자 제목.
contentTEXT · 필수비어 있지 않은 후보 본문.
keywords_jsonJSON 배열 TEXT · 필수 / 기본 []검색용 키워드. 생성 함수는 정규화 후 최소 한 개를 요구. MCP 응답에서는 keywords 배열로 표현.
statusTEXT · 필수 / 기본 pendingpending(대기), promoted(기억 반영 완료), rejected(저장 제외).
memory_refTEXT · 조건부promoted일 때 비어 있지 않은 값 필수. pending·rejected에서는 NULL. 현재 writer 형식은 memory://<memory_id>.
storage_plan_jsonJSON 객체 TEXT · 선택실행 전 검증을 통과한 저장 계획. MCP 조회 응답에서는 storage_plan 객체.
plan_fingerprint64자 TEXT · 선택정규화된 쓰기 계획의 SHA-256 지문. 저장 계획과 함께 NULL이거나 함께 존재.
created_atTEXT · 필수후보 생성 UTC 시각.

pending은 미검토만 뜻하지 않는다. 계획 없이 검토를 기다리는 후보와, 계획은 있지만 실제 저장·상태 마감이 끝나지 않은 후보 모두 pending일 수 있다. 별도 error 상태·실패 사유 컬럼은 현재 없다. 실패는 도구 응답으로 알린다.

후보 테이블에는 관계 전용 행, Artifact 연결, 범용 버전 컬럼을 추가하지 않는다. State DB와 MemoryGraph 사이에 SQL 외래키를 만들지 않으며 실제 참조 형식은 writer 응답을 따른다.

6. Storage Plan · 후보에 보존하는 저장 계획

최초 MCP 입력은 {candidate_id, storage_plan}, 재시도 입력은 {candidate_id}다. 아래는 create 예시이며 ID와 내용은 설명용이다.

{
  "candidate_id": "MEMC-example",
  "storage_plan": {
    "decision": "create",
    "target_memory_id": null,
    "memory": {
      "type": "solution",
      "title": "SQLite 연결별 외래키 활성화",
      "content": "SQLite 연결마다 PRAGMA foreign_keys=ON을 실행한다.",
      "summary": "연결 직후 외래키 검사를 활성화한다.",
      "tags": ["sqlite", "foreign-key"],
      "importance": 0.8,
      "confidence": 0.9
    },
    "relationships": [{
      "direction": "outgoing",
      "target_memory_id": "existing-problem-id",
      "type": "SOLVES",
      "strength": 0.9,
      "confidence": 0.9,
      "context": "연결별 외래키 누락 문제를 해결한다."
    }],
    "reason": "score=8/10; create; 재사용할 검증된 해결책"
  }
}
계획 필드의미·조건
decisioncreate / merge / reject. 신규 저장 / 기존 기억 병합 / 제외.
target_memory_idmerge는 존재하는 대상 ID 필수. reject는 비움.
memorycreate·merge는 type/title/content 필수. summary/tags/importance/confidence는 선택 보강값. merge는 기존 정보를 보존한 완성본. reject는 null.
relationships[]기준 노드에서 나가는 outgoing 또는 들어오는 incoming, 존재하는 대상 ID, 공식 관계 타입. 자기 연결·중복은 거부. reject는 빈 배열.
reason판정 이유. 저장 도구에서는 선택값이지만 스킬은 점수·결정·근거를 적도록 지시한다.

계획 지문은 정규화된 decision, target_memory_id, memory, relationships의 쓰기 내용으로 계산하며 설명용 reason은 제외한다. 저장된 계획과 다른 지문의 재시도는 거부한다. 후보의 원래 제목·본문은 작업 중 입력이고, 최종 기억 내용은 이 계획에 따로 보존된다.

Receipt · 실제 저장 결과 응답

ok, status(validated/committed/partial/validation_error/conflict), candidate_id, decision, 선택적인 memory_id·memory_ref·node_result, relationships.created/skipped/failed 배열, warnings, 선택적인 error.code/message를 제공한다. Adapter의 already_finalized 응답 등 일부 경로는 필드를 생략할 수 있다. 이 응답 status는 후보 테이블 status와 다르다.

7. 연결 관계와 변경 경계

runs.id ← memory_candidates.run_id
memory_candidates.storage_plan_json → 최종 Memory 내용·관계 계획
memory_candidates.memory_ref = memory://candidate:MEMC-example
                                      └─ memories.id = candidate:MEMC-example
relationships.from_id / to_id → memories.id

하나의 후보는 create면 새 기억, merge면 기존 기억 하나를 가리킨다. 하나의 기존 기억에 여러 후보가 병합될 수 있다. 후보 상태 마감은 Memory MCP 내부에서만 수행하며 직접 promote·reject MCP는 공개하지 않는다.

MemoryGraph 기본 구조는 외부 라이브러리 소스가 관리하고, Harness 후보 DDL은 저장소가 관리한다. 이 문서 통합은 스키마 변경이나 데이터 이전을 수행하지 않는다. 운영 시점·재시도·미완료 과제는 운영 문서에만 정리한다.
