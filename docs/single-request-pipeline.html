Harness v2 · current lifecycle

단일 Codex 요청 파이프라인

현재 코드와 스킬을 기준으로 한 요청이 WorkItem(WI, 지속해서 관리하는 작업), Run(한 번의 실행), 도구 기록, 검증, 종료까지 이어지는 순서를 설명한다.

읽는 기준

w/ 선택 요청의 전체 흐름이다. 일반 요청은 선택기를 열지 않는다. WI의 done은 Run 종료와 별도의 사용자 결정이다.

요청 입구흐름도시작·복구실행·기록마감예외용어

요청 입구

UserPromptSubmit(요청 시작 훅)은 프롬프트 맨 앞의 w/ 또는 W/를 확인한다.

일반 요청

UPS는 선택기를 열거나 상태 패킷을 넣지 않는다. 질문·설명은 그대로 진행한다. 활성 Run이 없다면 이 요청의 일반 도구 실행은 Harness의 Run 도구 기록으로 남지 않는다.

w/ 작업 요청

현재 세션의 이전 Run·Binding을 정리하고, 완료된 검토 계획 JSON을 청소한다. 선택 가능한 WI를 외부 터미널의 fzf에 보여준 뒤 선택 결과를 <work-selection-context>로 전달한다.

선택한 WI의 명시적 완료

$work-start가 완료 요청을 알아보면 close_work_item()으로 WI의 상태와 AC(완료 조건)·Evidence(충족 근거)를 검사한다. 이 분기는 새 Run을 만들지 않는다.

왜 Run 성공과 WI 완료를 분리하나?

Codex가 한 번의 Run을 마치자마자 WI를 done으로 닫으면, 사용자가 결과를 확인하고 수정 요청을 할 때 같은 WI에서 새 Run을 시작하기 어렵다. 따라서 성공한 Run은 WI를 ready로 돌려 추가 작업을 열어 두고, 사용자가 명시적으로 완료를 요청할 때만 close_work_item()이 AC·Evidence를 재검증한 뒤 done으로 닫는다. 완료 WI를 다시 여는 전이와 별도 대기 상태는 두지 않는다.

현재 등록된 PreToolUse(도구 실행 전 훅)는 .codex/hooks.json에서 활성화되어 있다. hook_policy.py의 위험 호출·활성 Binding 검사 정책이 적용되므로, Run 없이 하는 변경 호출은 이 정책의 허용 여부에 영향을 받는다.

한눈에 보는 흐름

단계를 누르면 담당 주체와 처리 내용을 볼 수 있다. 색은 Hook, Codex, Skill을 구분한다.

1 · UPS

w/ 요청에서만 실행한다. 현재 세션의 이전 Turn에 남은 running Run을 interrupted로 복구하고, 종료 Run의 오래된 Binding을 정리한다. 고아 Review Plan을 청소한 뒤 fzf 선택 결과를 Codex에 보낸다.

선택부터 Run 시작까지

Runtime Binding은 Codex의 세션·Turn을 WI와 Run에 연결하는 임시 포인터다. 실제 상태는 SQLite에서 확인한다.

UPS가 현재 세션을 복구한다

reconcile_current_session()은 DB 건강 상태와 현재 세션 Binding을 확인한다. 이전 Turn에 속한 running Run만 interrupted로 정리하고, 종료된 Run을 가리키는 Binding은 삭제한다. 다른 세션의 Run은 자동 변경하지 않는다. cleanup_orphan_review_plans()는 DB상 완전히 마감된 계획 파일만 제거한다.

사용자가 WI를 고른다

UPS는 ready WI와 backlog Draft WI를 요청 파일에 쓰고 별도 Terminal.app에서 fzf 선택기를 연다. 검증된 결과만 selection_status, 선택 WI ID·제목·Draft 여부, 복구 결과가 담긴 작은 패킷으로 Codex에 준다. 취소·시간 초과·오류는 작업 시작으로 간주하지 않는다.

$work-start가 준비와 과거 기록 복구를 한다

Draft면 refine_draft_work_item()으로 목표·다음 행동·AC를 갖춘 ready WI로 바꾼다. 그 뒤 list_runs_with_unreviewed_tool_events()로 선택 WI의 미검토 Run을 찾는다. 정상 Review Plan이 있으면 recover_review_plan()으로 적용하고, 없거나 손상됐으면 EVT·Artifact·Evidence·AC와 현재 맥락을 비교해 확신한 항목만 복구한다. 미검토 EVT가 남으면 새 Run을 만들지 않는다.

새 Run을 열고 기억을 불러온다

get_work_context()에서 현재 목표와 AC를 읽고 start_work(intent, recall_query)를 호출한다. intent는 이번 실행 목적, recall_query는 장기 기억 검색어다. 전용 PostToolUse가 Binding을 만든 뒤 MemoryGraph에서 관련 기억을 조회한다. Binding 저장에 실패하면 방금 만든 Run을 interrupted로 보상 정리한다.

fzf를 왜 별도 터미널에서 실행하나?

UPS의 표준 입출력은 Codex와 Hook JSON을 주고받는 통로라서 대화형 fzf 화면으로 사용할 수 없다. UPS와 선택기는 상태 DB 옆 selections/selection-<request_id>.request.json·.result.json 임시 파일로 통신한다. MCP Elicitation이나 모델의 WI 자동 매칭은 사용하지 않는다.

선택 결과는 어떻게 검증하고 정리하나?

요청마다 고유한 request_id(선택 요청 ID)를 만들고, 결과의 요청 ID·session_id(세션 ID)·turn_id(요청 턴 ID)가 일치하는지 확인한다. 선택된 WI가 원래 목록에 있고 결과가 만료 시각 전인지도 검사한다. 기본 대기는 300초다. 취소·시간 초과·터미널 종료·검증 실패는 새 Run을 시작하지 않으며, UPS는 해당 요청의 임시 파일을 정리한다.

작업 중 도구 기록

기계적인 실행 기록과 의미를 판단한 결과를 분리한다.

PreToolUse · 실행 전

현재 설정에는 정책 훅이 등록되어 있다. hook_policy.py가 호출을 조회·준비·활성 Run 필요·위험으로 분류하고, 필요한 경우 validate_active_binding()으로 세션 Binding과 DB 상태를 대조한다.

PostToolUse · 실행 후

활성 Binding이 있을 때 일반 도구 실행을 run_tool_events에 EVT로 저장한다. pwd·ls 같은 조회도 기록 대상이다. harness-state·harness-memory MCP 호출과 start_work·finish_work 수명주기 처리는 일반 EVT 목록에서 제외한다.

Codex · 의미 판단

이후 세션에서도 재사용할 지식은 작업 중 create_memory_candidate()로 후보를 남긴다. EVT가 Artifact나 AC의 Evidence가 되는지는 마감 시 문맥과 함께 검토한다.

EVT 저장이 실패해도 이미 실행된 도구 결과를 취소하지는 않는다. PostToolUse가 실패한 도구 이름·요약·이유를 Codex 문맥에 알리고, $work-finish가 그 알림도 결과 검토에 포함한다.

$work-finish 마감 순서

Artifact는 Run의 작업 결과, Evidence는 그 결과와 WI 완료 조건을 연결한 근거다. Codex가 의미를 판단하고 DB 함수가 일관성을 검사한다.

Postflight와 EVT 목록을 읽는다

get_postflight_status()로 활성 Run·AC·Artifact·pending 기억 후보를 확인한다. list_run_tool_events()의 전체 목록과 snapshot_max_seq(검토 대상 마지막 EVT 순번)를 읽는다. 단순 조회·중간 확인은 빠르게 제외하고 실제 결과를 검토한다.

Run별 Review Plan JSON을 고정한다

각 EVT를 artifact_evidence, artifact_only, exclude로 분류한다. 새 v2 계획은 등록할 EVT의 판단·사유를 decisions에, 제외할 EVT의 ID만 excluded_event_ids에 넣어 save_review_plan()으로 .harness/review-plans/<run-id>.json에 저장한다. JSON은 이 시점의 판단과 EVT ID만 고정하며, 이후의 DB 적용 결과나 도구 입력·출력 원문을 복사하지 않는다. 과거 v1 계획도 복구할 수 있다.

Artifact·Evidence와 기억 후보를 처리한다

등록할 EVT마다 apply_review_plan_event(run_id, event_id)를 호출한다. 도구가 저장된 Review Plan의 값으로 Artifact를 등록하고 필요한 Evidence를 연결·판정한다. pending Memory Candidate(장기 기억 저장 후보)는 $memory-finalize로 가치·중복·관계를 검토한다. 후보가 끝내 pending으로 남아도 Run 종료 자체는 차단하지 않는다.

검토 마감과 재확인을 한다

Postflight를 view="final"로 다시 읽어 Run·완료 검증·pending 후보 ID만 확인한다. finalize_review_plan()이 적용된 계획 EVT에 reviewed_at(검토 마감 시각)을 기록하고 입력·결과 요약을 한 DB 트랜잭션에서 지운다. 스냅샷 뒤에 생긴 EVT(run_seq > snapshot_max_seq)도 별도 A/E 추론 없이 마감한다. 마감 결과에 누락·불일치가 있거나 호출이 실패했을 때만 get_run_review_status()로 재확인하고, 수정 가능한 원인이면 최대 한 번 재시도한다.

Run을 종료하고 계획 파일을 정리한다

finish_work()는 실제 결과에 맞는 outcome으로 Run과 WI를 갱신한다. progressed면 Run은 succeeded, WI는 다시 ready가 된다. 성공한 호출의 PostToolUse가 Binding을 지운다. Run 종료와 EVT 검토·요약 제거가 모두 끝나면 delete_review_plan()으로 JSON을 삭제한다. WI의 done은 사용자가 웹 콘솔이나 명시적 완료 요청으로 별도 처리한다.

중단·복구 경계

Hook은 실행 결과의 의미를 대신 판단하지 않는다. 소유권이 확인된 상태만 기계적으로 정리한다.

이전 Turn의 Run이 계속 running이면?

다음 w/ 요청의 UPS가 현재 세션 Binding의 이전 turn_id를 확인해 해당 Run만 interrupted로 복구한다. 남은 미검토 EVT는 WI 선택 뒤 $work-start가 새 Run 전에 처리한다. 다른 세션 Run은 자동 종료하지 않는다.

Review Plan이 없거나 손상됐으면?

$work-start는 해당 Run의 EVT·Artifact·Evidence·AC와 사용 가능한 맥락을 대조한다. 확신할 수 있는 항목만 복구한다. 손상 JSON을 그대로 남기고, 판단할 수 없는 EVT가 있으면 ID와 이유를 알리며 새 Run 시작을 멈춘다.

Stop Hook은 언제 한 번 더 실행시키나?

현재 세션 Binding이 일치하는 running Run이 있으면 첫 Stop에서 $work-finish 실행을 지시한다. 두 번째 Stop의 stop_hook_active=true는 경고 후 통과한다. pending 장기 기억 후보만으로는 Stop을 막지 않는다.

Review Plan JSON이 남았지만 DB상 마감됐다면?

Run 종료 뒤 delete_review_plan()이 제거한다. 삭제가 누락되면 다음 w/ UPS의 cleanup_orphan_review_plans()가 DB의 종료·검토 완료 상태를 확인하고 정리한다.

짧은 용어표

상태 필드와 함수 이름을 읽을 때 필요한 뜻만 모았다.

WI · Run · Binding

WI는 계속 관리하는 목표, Run은 그 목표를 처리하는 한 번의 실행이다. Binding은 현재 Codex 세션·Turn이 소유한 WI와 Run을 가리키는 임시 파일이다.

EVT · reviewed_at

EVT는 일반 도구 사용의 압축 기록이다. reviewed_at은 그 기록의 Artifact·Evidence 판단이 마감된 시각이며, 비어 있으면 복구 대상이다.

Review Plan · snapshot_max_seq

Review Plan은 EVT별 저장 판단을 고정한 Run별 JSON이다. snapshot_max_seq는 그 판단에 포함된 마지막 EVT 순번으로, 이후 생성 기록을 구별한다.
