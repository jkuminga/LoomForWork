# LoomForWork 버전과 업데이트 기준

현재 공개 버전은 `0.1.0`이다. 버전은 `큰 변화.기능 변화.수정` 순서로 읽는다.

| 다음 버전 | 언제 쓰나? | 예시 |
| --- | --- | --- |
| `0.1.1` | 기존 사용법을 유지하면서 문제를 고칠 때 | 설치 오류, 보안 문제, 잘못된 안내 수정 |
| `0.2.0` | 사용자가 체감할 새 기능을 넣거나 사용법·설정을 바꿀 때 | 새 작업 도구, 설치 방식 또는 작업 흐름 변경 |
| `1.0.0` | 핵심 사용법과 업데이트 방식을 안정적으로 지원할 준비가 됐을 때 | 기존 설치본의 업데이트까지 검증한 안정 버전 |

`0.x.x`는 아직 발전 중인 버전이다. 따라서 위 표는 엄격한 외부 규칙이라기보다 LoomForWork에서 일관되게 사용할 **권장 기준**이다. 특히 기존 설치본이 깨질 수 있는 변경은 `0.1.1` 같은 수정 버전에 담지 않고, `0.2.0`처럼 기능 버전을 올려 변경 사항과 이전 방법을 안내한다.

## 언제 게시할까?

WI(WorkItem, 하나의 목표와 완료 조건을 가진 작업 항목) 하나가 끝날 때마다 게시할 필요는 없다. 관련된 WI를 묶어 **사용자에게 쓸 만한 결과가 준비됐을 때** 새 버전을 낸다. 반대로 이미 게시한 버전의 중요한 오류라면 수정 한 건만으로도 `0.1.1`을 낼 수 있다.

한 번 게시한 `loomforwork@0.1.0`의 내용은 바꿀 수 없다. 수정해서 다시 게시하려면 반드시 새 버전 번호를 사용한다.

## 다음 버전을 내기 전에

1. 이번 변경이 수정인지, 새 기능이나 사용법 변경인지 판단해 버전을 정한다.
2. 새 프로젝트에서 설치하고, **기존 `0.1.0` 설치 프로젝트에서 업데이트**해 본다. 설치와 업데이트는 서로 다른 경로다.
3. `installer/update-compatibility.json`의 `compatible_from`에 **실제로 직접 업데이트를 검증한 기존 버전**을 넣는다. 이 목록은 설치기가 업데이트를 허용할 이전 버전 목록이다.
4. 배포 파일과 필수 기능을 확인한 뒤 새 버전을 게시한다.

현재 `compatible_from`은 빈 목록이다. 따라서 이 상태 그대로 다음 버전을 게시하면 `0.1.0` 설치본에서 `bunx loomforwork@latest update`가 거부된다. 다음 릴리스에서는 업데이트 검증과 호환 목록 반영이 먼저 필요하다.

참고: [Semantic Versioning](https://semver.org/), [npm 패키지 게시 규칙](https://docs.npmjs.com/cli/v12/commands/npm-publish/)
