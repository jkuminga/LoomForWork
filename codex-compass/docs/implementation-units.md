# 작업 단위 분해 가이드

이 문서는 프로젝트 목표를 Feature와 WorkItem으로 **어떻게 나눌지** 다룬다. WI 선택, Run 시작·종료, 결과 저장 절차는 [단일 요청 파이프라인](single-request-pipeline.html)과 [상태 저장소](state-store.html)를 따른다.

## 단위 구분

| 단위 | 의미 | 예시 |
| --- | --- | --- |
| Feature | 여러 작업을 묶는 큰 목표나 기능 영역 | 프로필 관리 |
| WorkItem (WI) | 독립적인 목표와 완료 조건을 가진 작업 항목 | 사용자가 닉네임을 수정하고 저장할 수 있다 |
| Run | 하나의 WI를 진전시키는 한 번의 실행 | 닉네임 입력·저장 흐름 구현 |

Feature 없이 WI를 만들 수도 있고, 하나의 WI를 여러 Run에서 이어서 진행할 수도 있다. WI는 구현뿐 아니라 조사, 결정, 설계, 검증에도 사용할 수 있다. 완료 조건(AC, Acceptance Criteria)은 WI의 목표 달성 여부를 확인하는 기준이다.

## 기존 WI를 이어갈지 새 WI를 만들지

먼저 묻는다.

> 기존 WI를 완료하려면 이번 작업도 필요한가?

그렇다면 대개 같은 WI에서 이어간다. 별도로 완료할 수 있는 목표이거나, 기존 WI가 끝나도 독립적인 후속 작업으로 남거나, 다른 완료 조건이 필요한 경우에는 새 WI로 나눈다. 단순한 파일 수정 한 건이나 질문 하나를 기계적으로 새 WI로 만들 필요는 없다. 반대로 변경 파일이 여러 개라는 이유만으로 새 WI가 필요한 것도 아니다.

WI를 언제 선택하고 Run을 언제 시작하는지는 작업 단위 판단과 별개다. 현재 `w/` 요청은 사용자가 WI를 선택하는 흐름을 사용하며, 작은 일반 요청까지 자동으로 WI에 연결하지 않는다. 선택·복구·시작의 세부 동작은 [단일 요청 파이프라인](single-request-pipeline.html)을 참고한다.

## 제품 기능은 세로로 분해

제품 기능은 DB·API·UI 같은 기술 층만으로 나누기보다, 가능하면 사용자가 확인할 수 있는 작은 흐름으로 나눈다. 한 WI가 목표 달성에 필요한 여러 층을 함께 수정할 수 있다.

```text
Feature: 프로필 관리
  WI: 로그인 사용자가 자신의 프로필을 조회할 수 있다
      → 필요한 조회, API, 화면 표시, 검증
  WI: 사용자가 닉네임을 수정하고 저장할 수 있다
      → 입력 검증, 저장 API, UI 피드백, 테스트
  WI: 사용자가 프로필 이미지를 업로드할 수 있다
      → 파일 검증, 저장, 업로드 UI, 테스트
```

작업 성격에 따라 다른 분해 기준도 쓸 수 있다.

| 기준 | 적합한 경우 |
| --- | --- |
| 사용자 흐름 | 독립적으로 동작·검증할 수 있는 기능 조각 |
| 위험 우선 | 외부 연동, 권한, 성능 등 불확실성이 큰 부분 |
| 결정·조사 | 구현 전에 답해야 할 별도 설계 질문 |
| 기술 기반 | 여러 기능이 공유하는 기반이나 내부 구조 변경 |
| 마이그레이션 단계 | 준비 → 호환 → 전환 → 제거가 필요한 변경 |

한 Feature 안에서 여러 기준을 조합해도 된다. 예를 들어 결제 연동은 웹훅 중복 수신 정책을 먼저 결정하고, 결제 요청·완료·실패 흐름을 각각 구현·검증할 수 있다.

## 좋은 WI의 기준

- 목표를 한 문장으로 설명할 수 있다.
- 결과를 확인할 완료 조건을 적을 수 있다. 조건 개수는 고정 규칙이 아니다.
- 작업 중단 시 남은 일과 다음 행동을 설명할 수 있다.
- 너무 넓어서 서로 무관한 목표를 한꺼번에 담지 않는다.
- 너무 작아서 독립적인 완료 판단이 무의미한 실행 단계 하나만 담지 않는다.

```text
너무 넓음: 인증 시스템 구현
적절함: 만료된 세션의 API 요청에 재로그인 응답을 반환한다
너무 작음: API 파일 하나를 생성한다
```

설계부터 구현까지 하나의 목표로 잡았다면 설계 대화만 마쳤다는 이유로 WI를 완료하지 않는다. 완료 조건이 실제 화면·코드 변경까지 요구한다면 그 결과를 검증할 때까지 같은 WI에서 진행한다.

## 계획의 상세도

전체 방향과 Feature는 거칠게 잡고, **다음에 실행할 WI만 구체적으로 정의**한다. 진행 중 드러난 요구사항이 현재 WI의 완료에 필요하면 같은 WI에 반영하고, 독립적으로 완료해야 할 목표일 때 새 WI를 추가한다.

WI 상태와 완료 절차, Run 및 Artifact(실행에서 얻은 작업 결과 기록)·Evidence(완료 조건의 근거) 연결은 이 문서에서 중복 정의하지 않는다. 각각 [상태 저장소](state-store.html)와 [단일 요청 파이프라인](single-request-pipeline.html)의 현재 규칙을 따른다.
