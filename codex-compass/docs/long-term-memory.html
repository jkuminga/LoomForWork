HARNESS V2 · MEMORY · 2026-10-16

장기기억 운영·구현

작업 중 발견한 재사용 지식은 State DB에 후보로 남기고, 검토를 통과한 기억과 관계만 MemoryGraph에 저장한다. 시작 시에는 관련 기억만 짧게 조회한다. 기억 저장 실패나 pending 후보는 Run 종료를 막지 않는다.

동작·책임·실패 정책은 이 문서, 필드·타입·제약은 장기기억 스키마를 따른다. 현재 저장소 코드 기준이며, 외부 제품의 최신 버전 안내가 아니다.

역할전체 흐름기억 조회후보 기록검토·저장실패·재시도구현·버전남은 보강

1. 같은 사실의 정본을 나눈다

State DB · 지금의 작업과 검토 전 후보

<git-common-dir>/harness-data/state.db는 WI(작업 목표), Run(한 번의 실행), 결과·완료 조건과 memory_candidates(장기기억 후보)를 저장한다. 후보의 저장 계획과 처리 상태도 이곳이 정본이다.

MemoryGraph · 다음에도 재사용할 지식

<git-common-dir>/harness-data/memorygraph.db는 검토된 Memory(기억 한 건)와 기억 사이의 방향 관계를 저장한다. 진행률·일회성 상태·대화 전문·도구 로그를 대신 보관하지 않는다.

두 DB는 별도 SQLite 파일이다. 후보는 run_id로 실행에 연결되고, 저장 성공 후 memory_ref(실제 기억 참조)로 MemoryGraph를 가리킨다. 필드 상세는 후보 스키마에만 정의한다.

2. 한 작업에서의 흐름

  1. 01 · 시작start_work() 성공 후 PostToolUse가 Binding(세션↔Run 연결)을 저장하고 관련 기억을 조회한다.
  2. 02 · 발견메인 Codex가 작업 맥락에서 재사용할 지식을 발견하면 후보를 즉시 한 건씩 기록한다.
  3. 03 · 검토$work-finish가 현재 Run의 후보를 $memory-finalize로 검토한다.
  4. 04 · 저장·마감MCP 저장 도구가 계획 보존·실제 기억 반영·후보 상태 변경을 처리한다. 실패한 후보는 보존하고 Run 마감은 계속한다.

Hook(생명주기 자동 처리)은 저장 가치를 추론하지 않는다. 별도 저비용 서브에이전트에 후보 판단을 병렬 위임하는 구조도 현재 사용하지 않는다. 일반 도구 로그와 Artifact·Evidence 검토는 단일 요청 파이프라인의 마감 흐름에서 설명한다.

3. Recall · 관련 기억만 짧게 조회

Codex가 Run 시작 때 recall_query(공백 구분 핵심어 2~5개)를 전달한다. 시작 전용 PostToolUse는 프로젝트 명령 codex-compass/bin/harness-memory recall을 실행한다. Wrapper(외부 라이브러리를 감싸는 연결 모듈)는 고정된 SQLiteBackend의 searchMemories()를 직접 사용하며 사람용 CLI 출력은 파싱하지 않는다.

  1. 키워드의 공백·빈 값·대소문자 중복을 정규화한다.
  2. 키워드마다 따로 검색하고 같은 Memory ID는 병합한다.
  3. 매칭 키워드 수 → 중요도 → 최신 시각 순으로 내림차순 정렬한다. 완전 동점은 ID 오름차순으로 고정한다.
  4. 기본 5개를 반환한다. Wrapper의 허용 범위는 1~10개이며 Hook은 기본 제한으로 짧은 문맥을 전달한다.
codex-compass/bin/harness-memory recall "sqlite foreign-key" --limit 5

{"ok":true,"memories":[{"id":"mem-example","title":"연결별 외래키 활성화",
"summary":"SQLite 연결마다 외래키 검사를 켠다.","matched_keywords":["sqlite"]}],"warnings":[]}

Wrapper JSON은 ID를 포함하지만 모델에게 주입하는 Context Packet(추가 문맥)은 Hook에서 제목·요약·매칭 키워드 위주로 더 축약한다. 빈 키워드는 DB 조회 없이 빈 성공 결과를 낸다. 일부 검색 실패는 성공 결과와 경고를 함께 반환하고, 전부 실패하면 ok=false와 memory_database_unavailable 경고를 반환한다. 조회 실패로 이미 시작된 Run을 되돌리지 않는다.

4. 후보는 발견 즉시 기록

AGENTS.md의 지침에 따라 활성 Run에서 harness-state.create_memory_candidate()를 호출한다. 내부 DB 함수는 create_candidate()다. 입력은 run_id, 종류 초안, 제목, 내용, 검색 키워드다. 최소 하나의 유효한 키워드가 필요하다. long-term/*.json 실험 경로는 사용하지 않는다.

후보로 남긴다

  • 확정된 설계·기술 선택과 이유
  • 재현된 문제 원인과 검증된 해결책
  • 다른 세션에서도 재사용할 절차·명령·제약
  • 기존 기억을 대체하거나 바로잡는 결정

후보로 남기지 않는다

  • 진행률·단순 수정·임시 경로
  • 근거 없는 추측·이해 불가능한 문장 조각
  • 비밀정보·인증정보·개인정보
  • 도구 출력이나 대화의 전문

일반 요청에서 활성 Run이 없다면 후보 생성 DB 함수가 거부한다. 일반 파일 편집 허용 여부와 기억 후보의 Run 소속 검증은 별개의 정책이다.

5. 후보 검토와 실제 저장

주체책임
$work-finishget_postflight_status()로 현재 Run의 pending 후보를 읽고 후보별로 기억 검토 스킬을 실행한다.
$memory-finalize후보의 가치·중복·최종 타입·관계를 판단하고 Storage Plan(실행할 저장 계획)을 만들어 저장 MCP를 호출한다.
inspect_memory_candidate()pending 후보 한 건과 유사한 기존 기억을 읽는다. 추가 검색어를 선택적으로 받으며 기본 5개·최대 10개를 반환한다. 검색어 최대 5개, 본문 미리보기 최대 800자 및 잘림 표시를 제공한다.
finalize_memory_candidate()전체 계획 검증 → State DB 계획 보존 → MemoryGraph 쓰기 → 후보 상태 변경을 수행한다. Python MCP와 Bun JSON Bridge(프로세스 연결)가 내부 구현을 감춘다.

검토는 강제 제외를 먼저 적용한 후 재사용성·장기 유효성·독립적인 유용성·근거·영향도를 10점으로 평가한다. 7점 이상이면 저장을 검토하고 6점 이하는 제외한다. 같은 내용과 근거는 reject(저장 제외), 기존 주제 보강은 merge(병합), 독립적인 새 지식은 create(신규 저장)다.

타입 초안은 힌트일 뿐이며 최종 기억 타입은 사용 목적에 따라 정한다. 관계는 확실한 것만 최대 3개를 제안하고, 방향과 기존 대상 ID를 지정한다. 임의의 기존 노드 둘 사이를 연결하지 않는다. 상세 채점·모델 판단 규칙은 스킬과 평가 기준을 따른다.

merge는 자동으로 본문을 합쳐주는 기능이 아니다. 모델이 기존의 유효한 정보와 새 정보를 합친 완성본을 제공해야 한다. 기존 내용 축약·제거가 필요하면 이유를 기록한다. 입력 스키마·완전한 JSON 예시는 저장 계획 계약을 참고한다.

6. 실패·재시도와 종료 정책

처음에는 finalize_memory_candidate(candidate_id, storage_plan)을 호출한다. 쓰기 전 검증을 통과한 계획을 State DB에 보존하며, 이후 재시도는 finalize_memory_candidate(candidate_id)로 같은 계획을 재사용한다. 계획 지문이 달라지면 충돌로 거부한다.

결과후보 상태와 다음 행동
committed · 저장 완료create·merge는 promoted, reject는 rejected. 이미 마감된 같은 계획은 중복 쓰기 없이 완료 응답을 반환한다.
validation_error · 입력 오류실제 계약과 대조해 한 번 고쳐 호출한다. 이미 계획이 보존됐다면 새로운 계획으로 바꾸지 않는다.
partial · 일부 성공노드·관계 등 성공분을 삭제하지 않고 후보와 계획을 pending으로 보존한다. 같은 턴에서 반복 호출하지 않는다.
conflict · 충돌 / 도구 실패계획·기존 데이터·오류를 알린다. 결과를 추측해 후보 상태를 직접 바꾸지 않는다.

create의 노드 ID는 candidate:<candidate_id>로 고정된다. 관계는 같은 출발·도착·타입이면 재생성을 건너뛴다. 저장 후 같은 노드인지 비교하고, 같은 계획이 쓴 병합 대상에 다른 내용이 생기면 덮어쓰기 대신 충돌을 낸다.

두 DB를 아우르는 단일 트랜잭션을 구현한 것은 아니다. 기억은 저장됐지만 후보 상태 마감이 실패할 수 있으며, 같은 계획의 재호출로 이미 저장한 노드·관계를 재사용한다. DB 전체 장애는 이 문서에서 완전 복구를 보장하지 않는다.

종료는 계속한다. pending 후보가 남아도 $work-finish와 finish_work()는 그것만으로 Run 종료를 막지 않는다. Stop Hook도 기억 후보를 검사해 재실행하지 않는다. 남은 수·실패 원인은 사용자에게 알리며, 다음 UPS·work-start에서 과거 기억 후보를 자동 재처리하지 않는다.

7. 구현 위치와 버전 선택

MemoryGraph는 vendor/memory-graph 일반 파일의 v0.13.0, 실제 소스 커밋 67fc4f97816aa75823ae2dd4eff49f150cc6f1da로 고정한다. 필요한 TypeScript/Bun SQLite API를 제공하는 정식 릴리스를 선택해 재현성을 확보했다. 최신 버전이라는 뜻은 아니다. 태그 이후 offset·관계 탐색 보강은 초기 Recall에서 쓰지 않아 당시 채택하지 않았다.

CLI 실행 부작용을 피하려고 최상위 ts/src/index.ts 대신 backend 모듈을 직접 import한다. Bun 최소 요구는 1.1이며, 기존 로컬 검증 환경은 1.3.9다. 전역 CLI 설치는 필수 의존성이 아니다. MIT 라이선스와 고지를 유지하고 업그레이드는 별도 검증 후 수행한다.

위치역할

recall.ts / inspect.ts시작 시 짧은 기억 조회 / 후보와 유사 기억 비교 자료 조회.

설치·검증 명령

개발 저장소 루트에서 실행한다. test:python은 루트 tests/ 전체를 하네스 Python 환경으로 실행한다.

테스트는 임시 DB를 사용해야 한다. DB 파일과 WAL·SHM 보조 파일은 Git에서 제외하고, 원본 로그·프롬프트·비밀정보를 기억이나 Receipt(실행 결과 응답)에 넣지 않는다.

키워드 기반 Recall은 관계 그래프 BFS 확장, 전역·다중 프로젝트 통합, 별도 관측 플랫폼, 라이브러리 타입 확장까지 제공하지 않는다. 기억 DB는 같은 Git 저장소의 worktree가 공유하는 <git-common-dir>/harness-data/memorygraph.db에 둔다.

8. 기존 보강 과제의 보존

기존 긴급 보강 문서를 삭제하면서 미완료 과제를 완료로 간주하지 않는다. 후보 생성의 DB 통일과 직접 promote·reject MCP 우회 제거는 구현돼 있다. 아래 항목은 별도 보강이 필요하다.

  • 병합 보존 검증: create·merge·reject와 재시도 테스트는 있지만, 기존 본문의 유효한 내용이 보존되는지 전용 계약·회귀 테스트로 더 명확히 검증할 필요가 있다.
  • 전체 경로 통합 검증: 실제 SQLite 노드·관계 저장과 Python MCP의 후보 마감은 각각 테스트한다. State DB → 실제 Python MCP → Bun CLI → MemoryGraph → 후보 마감을 한 번에 연결해 create·merge·reject·부분 실패 재시도까지 검증하는 범위는 별도 보강 과제로 남긴다.

테스트 위치: 실제 SQLite 통합, 저장 정책, Python MCP. pending 후보를 사용자가 나중에 재등록하는 UI는 현재 문서 통합 작업의 구현 범위가 아니다.

통합 출처: 기존 운영 전략·Recall Wrapper·저장 도구 설계·운영 보강·버전 선택 문서. 상세 필드 사전은 스키마 문서. 버전 근거: 고정 릴리스 · 저장소 내 backend.
